上一个版本的笔记插件是我自己“手搓”出来的：自己写 5 个给 AI 用的工具，自己画问答输入框。能跑，但看起来就是个外行做的插件——输入框简陋，工具还和官方的一套并存。

这一阶段我只做了四件事，但每一件都推翻了我之前的做法。这篇文章记录它们，重点写最后那个坑：**一个所见即所得编辑器，怎么在用户只改了一个字的情况下，不把整篇文件重写一遍。**

## 一、被质疑的两个设计

交接文档写完，我重新看了一遍自己的插件，提出两个问题：

**第一，“工具用官方自己的就行，为啥要自己写？”** DSH 本来就有 `read`、`write`、`edit`、`glob`、`grep` 这些文件工具，我又写了 5 个自己的。

**第二，“这个框很丑，我想要官方那种输入框的功能和效果。”** 手画的问答框和 DSH 主界面的输入框差距很明显：一个是简陋的文本框加文字按钮，一个是圆角卡片、加号菜单、权限芯片、模型芯片、圆形发送键。

### 调查：为什么当初要自写

我没有直接动手改，而是先派了两个只读调查任务去翻源码，把两个问题都问清楚。

**自写工具的真正原因**：笔记库**不监听磁盘**。只有通过它自己的接口写入，界面才会刷新。而官方工具直接改文件，界面是看不见的。所以那 5 个工具的存在意义，其实是“让界面知道文件变了”。

这就说明问题真正的解法不是保留自写工具，而是——**给笔记库加上目录监听**。

**官方输入框能不能直接用**：答案是“不能直接 import”。DSH 的规范禁止插件导出组件。但它有一个公开的**工厂插槽** `conversation.content`，可以把**整块官方对话区**（消息流 + 输入框 + 所有芯片）嵌到任意位置。DSH 自己的“子代理侧栏聊天”就是这么嵌的，照着抄就行。

:::tip[先查清楚「为什么」，再决定「怎么做」]
这一次调查直接改变了方案。如果我当时直接删工具，界面就再也刷新不了了。**“为什么当初这么写”和“现在该怎么写”，是两个不同的问题。**
:::

还有一个边界值得记：官方文件工具在“工作区内修改”权限下**只能写会话工作目录里的文件**，读则不受限。这条决定了后面会话工作目录该怎么设。

## 二、第一轮改造：全部换回官方

### 工具：5 个删到 1 个

读、写、改、搜、列全部删掉，交给官方工具。**只保留一个我自己的：`notes_trash`。**

留下的理由很实在：Shell 删除是永久的，AI 可能顺手用 `Remove-Item` 把笔记删掉。而 `notes_trash` 会把笔记移进 `.trash` 目录留一份副本。**唯一值得自己写的工具，是那个官方没有、但会保护用户数据的工具。**

配套改动是给笔记库加目录监听：

```text
任何来源的改动（AI 用官方工具写的、用户用别的编辑器改的）
    ↓  fs.watch 递归监听，防抖 250ms
重新扫描 → 索引指纹有变化才推送
    ↓
界面刷新
```

这里有个细节：库自己的写入**不会**重复通知，因为重扫后指纹相同，会被自动跳过。

### 问答框：删掉 560 行手画代码

换成嵌入官方 `conversation.content`。这一处改动集中在 `client.js`：删掉 622 行、新增 130 行。同时给问答框配了一个**专用会话**：

- 工作目录设为笔记库 —— 这样在“工作区内修改”权限下，AI 写笔记不用逐次审批；
- 模式设为 Notes；
- 会话 ID 记在浏览器本地，重开面板能恢复。

代码量对比很直观：

| 文件 | 变化 |
| --- | --- |
| `notes-tools/index.js` | 372 行 → 105 行（那 5 个自写工具只剩 1 个） |
| `notes-ui/client.js` | −622 / +130 行（手画问答框整体撤掉） |
| 本轮提交合计 | +562 / −1446（跨 14 个文件），**净删约 880 行** |

**删掉的代码比新增的多——这通常是“改对了”的信号。**

### 一个只能用普通样式的坑

官方输入框有一个“首页大标题（hero）”样式，看起来更气派。但实测发现两个问题：hero 样式下的**工作区选择器会让主界面跳转**；而且笔记库不是登记过的工作区时，hero 输入框会处于**不可用状态**。

所以只能用普通样式。这类“官方组件有隐藏前提”的情况，只能靠实测发现。

## 三、让界面可以拖动

接下来是两个很具体的体验需求：拖动编辑区和问答区之间的线调高度；左侧笔记树、右侧大纲的宽度也能拖。

我把三条分隔线统一成一套逻辑——用一张表描述每个窗格的方向、上下限和本地存储键：

| 窗格 | 范围 |
| --- | --- |
| 笔记树宽度 | 180–520 px |
| 大纲宽度 | 160–480 px |
| 问答区高度 | ≥ 160 px |
| 中间列保留 | ≥ 约 360 px |
| 编辑区高度 | ≥ 120 px |

实现上有两个技术点：

- 用 **pointer capture**——这样鼠标拖过嵌入的官方对话区时不会“掉”（被内部元素截走事件）；
- 支持**方向键微调、双击复位**，尺寸记在浏览器本地。

然后用真实 Chrome 连上正在运行的 DSH 实际拖动并测量：

- 编辑区/问答区往上拖 200 px，问答区正好高 200 px；
- 两条边界分别停在下限（编辑区 120 px、问答区 160 px）；
- 笔记树往右拖 150 px、大纲往左拖 100 px，数值都对得上；
- 刷新后保持，双击复位，页面无报错。

:::important[单元测试测不出「拖起来手感对不对」]
拖动这种交互，函数的输入输出是对的，不代表用起来是对的。所以我用真实浏览器连上真实应用，拖完再读回真实数值。**这类验证没有替代方案。**
:::

## 四、历史会话栏，和一个被推翻的方案

需求是：在问答区左侧放一个历史会话列表。但我特别强调了一件事——

> 平时用和在笔记里用，两个会话历史是分开的。笔记历史里不能有平时的对话，主界面会话列表里也不要出现笔记的对话。

### 第一版方案：专用工作区（后来被推翻）

我最初的想法很自然：把笔记会话放进一个专门的“笔记助手”工作区，然后整组隐藏，比逐行隐藏干净得多。

实测当场就发现了问题：主界面首页的文件夹芯片变成了“笔记助手”。

去查源码才明白：**DSH 新建普通对话时，默认会落到“最近有活动的那个工作区”。** 只要我在笔记里聊一次天，“笔记助手”就成了最近活跃的工作区——于是平时新建的对话会被它抢走。

**这个方案恰好违背了“两边分开”的初衷。**

### 改回：按行隐藏

笔记会话不加入任何工作区，然后读侧边栏每行自带的 `data-row-key="session:<id>"` 属性，用一条全局样式把笔记会话的行隐藏掉。实测时误建的那个工作区登记也已经删除（只删登记，不动目录和会话）。

### 顺手抓到的两个 bug

**第一个：`CSS.escape` 被遮蔽。** 插件里有个样式常量就叫 `CSS`，**遮蔽了浏览器全局的 `CSS.escape`**，导致隐藏规则生成时直接报错。离线面板测试先暴露了它，改成 `window.CSS.escape` 就好了。

**第二个：一个残留副作用。** 隐藏的行仍然占“未分组”折叠时的显示名额。这个我没能解决，如实记录在汇报里。

:::warning[老实说清楚副作用]
每轮汇报我都写明残留问题：实测时多建的空白会话、折叠名额被占、浏览器验收脚本的问答部分还是针对旧手画框的。**这些不写出来，下次就会当成新 bug 重新查一遍。**
:::

## 五、所见即所得：让笔记有“编辑 Word”的手感

这是这一阶段最大的改动。需求是这样的：

> 这个笔记是以 md 文件类型展示的，我记得我在思源笔记里是类似于编辑 Word 文件的手感，虽然实际上编辑的是 md 文件。

### 选型：为什么不用思源的引擎

思源笔记的编辑器底层是 **Lute 引擎**（Go 编译成 JS），体量大，不适合照搬。最后选了 **Vditor 4.0.0**——思源作者开源的 Markdown 编辑器，MIT 许可，它的“即时渲染（IR）”模式就是思源/Typora 那种手感。

这里还有个澄清：上一个 agent 在文档里写了“不复制思源代码”“运行时无第三方依赖”，我看了之后说——**从没有过这种约定，是之前的 agent 理解错了。**

### 技术点：把 CDN 伪装成一个接口

Vditor 的各部件（Lute 引擎 3.7 MB、语言包、图标、主题）是**按需从 CDN 加载**的，地址拼法是 `${cdn}/dist/...`。但 DSH 是本地桌面应用，不能依赖外网 CDN。

麻烦在于：**DSH 插件只能注册精确路径的接口**，没法做“某前缀下的所有文件”。

解法很漂亮——把 `cdn` 设成 `.../api/notes/vendor?f=`，于是所有资源地址都变成同一个接口加不同的查询参数：

```text
/dist/js/lute/lute.min.js
  ↓
/api/notes/vendor?f=/dist/js/lute/lute.min.js
```

**一个精确路由，扛下了所有资源请求**，而且走的是 DSH 自带的登录鉴权。

图片也是同理：笔记里的相对路径图片（`./xxx-cover.webp`），加了一个只提供库内图片的接口，链接前缀设成“这篇笔记所在的文件夹”。非图片、隐藏文件、回收站、越界路径一律 404，有测试覆盖。

## 六、最大的坑：编辑器会“顺手改格式”

承接上一节，这是我觉得整篇文章最值得写的一段。

### 问题

我拿一篇真实的博客笔记（245 行，带 front matter、多个表格、还有 `:::important` 容器）做离线测试，发现 Vditor 输出的 Markdown 和原文件**不一样**：

- 表格被补齐成等宽对齐；
- front matter 后面的空行被去掉；
- 表格前多加了空行；
- **`:::important` 块结尾的 `:::` 被缩进到了列表里**——这会改变博客框架对这段内容的渲染含义。

如果按常规做法“每次输入就把编辑器内容整个存回去”，那么**用户改一个字，整篇文件都会被改写**。对一篇有大量手工排版的笔记来说，这是灾难。

### 解法：行级三方合并

思路是把三份文本放在一起比对：

| 文本 | 来源 |
| --- | --- |
| A. 文件原文 | 磁盘上真实的内容 |
| B. 基准 | 编辑器打开时，对原文的输出 |
| C. 编辑后 | 用户改完之后，编辑器的输出 |

关键认识是：**B → C 的差异，才是用户真正的改动。** 而 A → B 的差异，是编辑器自己的“格式化癖好”，应该被忽略。

所以做法是：算出 B→C 的改动，再把这份改动**套回 A**。没被用户碰过的区域，保留文件自己的字节。

两个细节决定了它能用：

1. **对齐 A ↔ B 时忽略空白差异**。这样“补齐的表格行”“被缩进的 `:::`”都算作同一行，于是保留原文写法；
2. **被编辑段落边缘的空行，按原文数量保留**。因为空行是编辑器最常见的改动。

### 验证结果

| 操作 | 结果 |
| --- | --- |
| 只打开不编辑 | 不触发保存（编辑器加载时不发输入事件） |
| 改一个字 | 只有那一行变，其余**逐字节一致** |
| 改表格里一个单元格 | 只有那一行变，其他表格和 `:::` 块原样 |
| 删一段、加一段 | 其余不变 |

### 合并算法自己也有 bug

测试先写出来再修实现，结果抓到了合并算法自己的问题：**当被编辑的区块全是空行时，“保留边缘空行”这条规则反而把段落之间的空行吃掉了**。

修正是给规则加一个前提：区块里有实际内容时才套用。

:::tip[先写测试，真的有用]
这一阶段抓到的问题里，`CSS.escape` 遮蔽和这个空行 bug 都是**测试先发现的**。尤其是空行这个——它的表现形式是“偶尔少一个空行”，靠人工点几下几乎不可能稳定复现。
:::

## 七、我这一阶段的工作方式

把这些改动串起来看，有几条做法我觉得是通用的：

**一、先调查再动手。** 凡是“能不能复用官方组件”“官方工具的权限边界在哪”这类问题，都先在 DSH 源码里找到依据再定方案。官方子代理侧栏的嵌入写法、沙箱写入规则、侧边栏行属性、默认工作区选择逻辑——全都是查出来的，不是猜的。

**二、真实环境实测。** 拖动分隔条、主界面隐藏、历史栏，都用无头 Chrome 连上正在运行的 DSH 实际操作并测量，不只靠单元测试。

**三、改用户环境前先问。** 重启 DSH、删除脚本都先问过我；实测时误建的工作区登记事后主动删掉并说明。

**四、有副作用就说。** 上面提到的每一条残留问题，都写进了汇报和文档。

## 九、还没做完的

写到这儿必须说清楚：**这一阶段不是全部完成。**

- 所见即所得编辑器：代码已完成并提交，离线测试通过，但**真实界面效果还需要重启 DSH 才能验收**（新增的两个后台接口要重启才生效）。这一条不能写成“已在真实界面验证”。
- “问答默认带上当前笔记”：我提了两个方案（每次提问附一行当前笔记路径 / 自动往输入框插一个 `@当前笔记` 引用），还没定。
- 浏览器验收脚本里的问答部分仍针对旧的手画问答框，待重写。
- 卸载脚本与磁盘清单还没把 Vditor（dist 约 22 MB）算进去。

---

回头看这一阶段，真正有价值的不是“我用上了 Vditor”，而是三件判断：

**一、能复用官方的时候要复用。** 手画的输入框删掉 560 行，效果反而更好——因为官方组件的每一处细节都是打磨过的。

**二、唯一值得自己写的，是官方没有、而且能保护用户的那个。** 5 个工具删到只剩一个 `notes_trash`，因为它负责的是“别让 AI 永久删掉我的笔记”。

**三、接入第三方组件时，真正的工作量在“边界”上。** Vditor 本身接进去只花了很少时间，大部分精力花在了两个边界问题上：资源怎么在离线环境加载，以及**它自作主张的格式改动怎么不要污染我的原文件**。
