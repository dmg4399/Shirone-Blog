这个博客不是我从零写出来的。我选了一套现成的 Astro 主题，然后花了几轮时间，把它一点点改成自己的样子：换掉标题、头像和社交链接，重做背景壁纸，清空示例文章，最后才开始写自己的内容。

这篇文章就是把那次改造完整复述一遍。它更像工程记录而不是教程：我会说明每个决定背后的取舍、改错了什么、哪里踩了坑，方便以后自己回看，也方便想改主题的人少走几步弯路。

## 一、先想清楚：为什么用主题，而不是自己写

自己写一个博客当然更自由，但我很快放弃了。真正要花钱花时间的地方不是页面，而是那些看起来不起眼、但少一个都不行的部分：

- 响应式布局和深色模式；
- 代码高亮、数学公式、图片响应式生成；
- 搜索索引、RSS、站点地图；
- 无障碍和首屏性能；
- 每加一个功能就要重新验证一次的一致性。

这些内容我自己写，大概要几周，而且改一次忘一次。主题已经把它们做完了，我需要做的只是**把它变成我的**。所以我的定位是：主题负责骨架和通用能力，我负责身份、内容和视觉。

选定之后我做的第一件事不是改代码，而是把仓库结构读一遍：哪里是配置、哪里是组件、哪里是内容。搞清归属，后面每一步都不会改错地方。

## 二、让站点在本地跑起来

这一步的目标只有一个：看到页面。命令记不住没关系，记住三条就够。

```powershell
pnpm.cmd install --frozen-lockfile   # 安装锁定版本的依赖
pnpm.cmd dev                         # 启动本地开发服务
pnpm.cmd check                       # Astro 类型与诊断检查
```

开发服务启动后访问 `http://localhost:4321/`。Windows 上要把 `pnpm` 写成 `pnpm.cmd`，否则可能找不到命令。

有两点经验：

1. **依赖一定用锁定安装。** 主题依赖多，`--frozen-lockfile` 能保证我本地跑通的版本和线上构建的一致。
2. **`pnpm.cmd check` 要养成在提交前跑的习惯。** 它必须报告 0 error。我早期改配置时写错一个字段名，页面看着正常，但类型检查已经报错；早点发现比上线后再查便宜太多。

## 三、第一步永远先改配置

我最开始的想法是直接去改组件，结果改了两处就发现：同样的文字在三个地方出现，改漏一处就不一致。后来才明白，这个主题是**配置驱动**的，大部分外观差异都不需要碰组件。

我把常见需求整理成一张对照表，改之前先查它：

| 我想改的东西 | 该去的地方 |
| --- | --- |
| 站点标题、副标题、语言、时区 | `src/config/siteConfig.ts` |
| 主题色、配色风格、色彩规范 | `src/config/siteConfig.ts` |
| 页面背景模式与全屏布局 | `src/config/siteConfig.ts` |
| 各页面开关（友链、番剧、相册等） | `src/config/siteConfig.ts` 的 `pages` |
| 头像、昵称、简介、社交链接 | `src/config/profileConfig.ts` |
| 侧边栏小组件与排布 | `src/config/sidebarConfig.ts` |
| 导航栏入口 | `src/config/navBarConfig.ts` |
| 音乐播放列表 | `src/config/musicConfig.ts` 与 `src/data/music.ts` |
| 界面文案 | `src/i18n/` |

举几个我实际改过的例子：

- **站点身份**：改 `siteConfig` 里的 `title`、`subtitle`、`lang` 和 `timeZone`。时区要写对，否则文章和动态的时间戳会出现在错误的那一天。
- **主题色**：我一开始想直接写死颜色，后来发现主题用的是 HCT 动态配色，只要给一个色相值，整套调色板会自己派生。改一个数字，比调十处颜色值稳得多。
- **背景模式**：`wallpaperMode.defaultMode` 决定访客默认看到横幅、全屏、覆盖透明还是纯色。访客在“显示设置”里的选择会存在浏览器里，覆盖我的默认值——所以它只是默认值，不是强制值。
- **页面开关**：不想要番剧页就把 `pages.anime` 关掉，导航入口和页面路由会一起收敛，不用再去删导航项。

:::tip[配置优先的检查方法]
改任何外观之前，先问一句：这会不会已经是一个配置项？在 `src/config/` 里搜一遍关键词，通常能省掉一次改组件的返工。
:::

## 四、把文案和内容元数据清干净

配置改完，界面标题已经是中文了，但我发现标签和分类还是英文。原因很简单：**它们不是界面文案，而是我文章里的元数据。**

界面里的固定文字属于 i18n，改动时要同步所有语言模块，缺一个语言就会在高亮时回退成默认文案。文章上的标签和分类则写在每篇文章的 frontmatter 里，改界面没有用。这两件事要分开处理。

我做的清理是：

- 把示例文章里的通用标签和分类换成中文，技术专有名词保留英文；
- 清掉示例文章、示例动态和示例配图，只留下页面功能本身；
- 保留归档、标签、分类这些页面的能力，内容清零后确认它们仍能正常打开。

:::warning[删示例内容前先留个底]
主题自带的示例文章同时充当语法文档，删掉之后就没法在站点里对照了。我删之前先把结构记了下来，才敢动手。
:::

清空后我逐个检查了首页、归档、动态、标签页和分类页。**空内容的页面最容易出问题**，因为没有数据时经常会漏掉兜底渲染。

## 五、换成自己的背景图

这是耗时最长的一步，也是视觉差别最大的一步。我的需求很朴素：人物构图好看、电脑和手机各自合适、放大不糊。

### 图片放哪里，决定了会不会被优化

主题对图片的处理规则很关键：

- 放进 `src/assets/` 的图片，会在构建时生成 AVIF 和 WebP 候选，并按宽度输出多档 `srcset`；
- 以 `/` 开头的 `public/` 路径和远程 URL 也能用，但保留原图，不生成候选。

所以我个人的背景图统一放在 `src/assets/images/banner/` 下面，分成 `desktop/` 和 `mobile/` 两个目录。桌面图给宽视口用，移动图只在小屏首页用，两者的裁切和构图可以完全不同。

### 分辨率是怎么定下来的

主题不会把一张图硬放大，它按“请求档位”和“源图宽度”取交集：

```js
// 桌面：请求这些档位，最终被源图宽度截断
[1280, 1600, 1920, 2560, 3840, 5120, 7680]

// 移动：同样按需生成，只是起点更低
[640, 828, 1080, 1440, 1920, 2560, 3840, 4320]
```

这里有个容易误解的点：**档位列表写得多，不等于访客会下载最大的图。** 浏览器按视口宽度乘以设备像素比挑最合适的那一档。我在 4K 屏幕上看到的是高分辨率版本，在手机上看到的还是手机档位，各取所需。

真正决定清晰度上限的是源图。源图只有 1080 宽，再怎么扩档位也没用。我吃过这个亏：一开始只放了一张小图，放大后明显发虚，换成高分辨率源图之后才彻底解决。

### 构图比分辨率更容易被忽略

电脑端和手机端的画面比例差很多，同一张图在电脑上人物居中，到手机上可能就被裁掉了。我的做法是分别提供两张图：电脑端保留原构图，移动端单独裁剪，让人物落在手机竖屏的中间。

### 视觉要跟着设计令牌走

改颜色、圆角、字号和动效时，我用的是主题已经定义好的令牌，而不是自己写死数值。这样做的好处是，之后换配色或调主题整体风格时，我改过的地方会一起变，不会留下一块和其他页面风格不一致的孤岛。

## 六、把内容真正换成自己的

前面都是装修，这一步才是搬家。文章放在 `src/content/posts/` 下，每篇文章一个目录，正文用 `index.md`：

```text
src/content/posts/
├── blog-renovation-guide/
│   ├── index.md
│   └── 配图.png
└── 另一篇文章/
    └── index.md
```

图片和文章放在同一个目录，正文里写相对路径引用。这样文章连同图片是一个整体，之后要移动、备份或单独拿出来，都不会散。

frontmatter 里我最常用的几个字段：

| 字段 | 作用 | 我的习惯 |
| --- | --- | --- |
| `title` | 标题 | 必填 |
| `published` | 发布日期 | 写 `YYYY-MM-DD`，不要带时间 |
| `publishedAt` | 精确发布时间 | 同一天发多篇时才加，带时区偏移 |
| `description` | 摘要 | 影响列表和搜索摘要，值得认真写 |
| `category` / `tags` | 分类与标签 | 中文，技术名词保留英文 |
| `draft` | 草稿 | 写作期间设 `true`，发布前改回 `false` |
| `image` | 封面图 | 不填会走无封面的渲染分支 |

日期这个坑我踩过：`published` 只能是日历日期，把时间塞进去会校验失败；要精确到时间就单独用 `publishedAt`，而且它必须落在 `published` 那一天之内。

### 自定义语法按需用

主题内置了一批 Markdown 扩展语法，写进正文就生效，不用开开关。我常用的是这几类：

- `:::tip[标题]` 与 `:::warning[标题]`：提示框，用来标出容易踩的坑；
- `:::steps{title="..."}`：步骤流，适合写操作流程；
- `:::tabs`：选项组，适合并列展示几种方案或平台差异；
- `::: collapse`：折叠面板，用来收长表格或附录；
- `==高亮==`：标记关键结论；
- `::github{repo="owner/repo"}`：引用一个仓库；
- `$公式$` 与 `mermaid` 代码块：数学公式与流程图。

不想记语法也没关系，用普通 Markdown 写完全可行。我用它们的原因只有一个：**让读者一眼看出哪句是结论、哪段是步骤、哪块是可以跳过的细节。**

## 七、发布：构建产物和托管平台

改造完成后要上线。这里有两件事要分清：**构建**和**托管**。

### 本地构建

发布产物只有一条命令：

```powershell
pnpm.cmd build
```

它会一次性做完内容同步、图标生成、图片派生、字体子集化、`astro build`、搜索索引生成和字体体积检查，最终产物在 `dist/`。看到 `dist/` 生成且没有报错，就说明这一版是可以交付的。

本地想先看一眼成品，可以起预览服务，而不是继续用开发服务：

```powershell
pnpm.cmd preview
```

### 托管平台的约定

静态托管平台通常只需要三项设置，主题里都留了对应的入口：

| 平台设置项 | 值 |
| --- | --- |
| Install 命令 | `pnpm install --frozen-lockfile` |
| Build 命令 | `pnpm build` |
| 输出目录 | `dist` |

仓库里保留了 `.github/workflows/deploy.yml.example` 作为部署流水线模板，里面给了几种常见平台的写法（产物直传、Pages 发布、自有服务器、平台自建构建触发）。要用的时候复制成 `deploy.yml`，把里面标注为占位的内容换成自己的，再接上平台凭据即可。

如果不打算用平台自建构建，也可以只让平台托管产物：本地或流水线构建出 `dist/` 之后直接上传。

:::important[发布前我固定会跑的一遍]
1. `pnpm.cmd check` —— 必须 0 error；
2. `pnpm.cmd check:manifest` —— 组件与语法清单一致性；
3. `pnpm.cmd type-check` —— 类型门禁；
4. `pnpm.cmd build` —— 完整构建；
5. 构建完成后抽查首页、一篇正文页和一张图片的实际路径。
:::

## 八、我踩过的坑

这部分比前面的步骤更值得记，因为每一步我都真的卡过。

**改样式没生效。** 大部分情况是构建缓存。改了 Stylus 或 Svelte 之后页面没变化，清掉 `node_modules/.vite` 和 `.astro` 再重启就好。改的是 Markdown 相关插件的话，还要顺带清 `.astro/data-store.json`。

**图片换了但页面还是旧的。** 浏览器和构建产物都可能拿着旧图。换图之后一定要在无痕窗口或者强制刷新下确认，不要凭开发服务的一次刷新判断成功。

**Windows 上构建报临时目录权限错误。** 这是环境问题不是代码问题。把构建用的临时目录指到项目内自己的目录就能绕过去，不要为此改构建配置。

**测试失败，但分不清是代码坏了还是测试过时了。** 我遇到过水波纹相关的用例失败：它期望首页移动端能看到水波纹动画，但代码已经把水波纹限定在横幅模式下，全屏布局时是隐藏的。这种情况下先去看组件里的显示规则，再判断该改代码还是改预期——我那次是**测试预期过时**，不是组件回归。

**首页文章卡片的封面点不到。** 浏览器测试里发现卡片的封面中心点击位置被正文区域挡住，但直接进文章链接是正常的。这是布局层级问题，不算致命，但我记了下来，等有精力再单独处理。

**音乐播放器有无障碍问题。** 扫描发现悬浮歌词里有隐藏区域仍然可以被键盘聚焦，播放器本身也缺少语义化的区域标记。功能能用，但离“能无障碍使用”还有距离。

**访问统计是占位的。** 资料卡上的“页面浏览”和“访问次数”当时只是外观占位，没有接真实统计服务，也没有开启上报。展示效果和真实数据是两件事，别把占位当成绩。

**最省事的弯路：想抄视觉。** 我拿别人站点当参考，真正有价值的是它的**组织和取舍**，不是它的颜色和排版。直接把别站的视觉抄过来，最后得到的是一个既不像别人、也不像自己的站点。

## 九、我现在的维护节奏

改造完成后，日常只剩写内容这一件事。我给自己定了一个简单的素材格式，想到什么就先按这个结构记下来，之后整理成文章会快很多：

```text
文章主题：
我的笔记、经历或初稿：
图片所在目录：
参考文章链接 / 喜欢的排版与语气：
标题、日期、分类、标签（可留空）：
草稿预览 / 正式展示：
```

写作时我坚持几条：原素材不覆盖；文章和配图放在同一目录；区分原稿和修订稿；引用题目或数据时回去核对原图；发布前检查内容、图片和页面入口。

回头看，这次改造真正花时间的不是任何一处技术难点，而是**把“主题的默认状态”一项一项换成“我的选择”**。配置给了大方向，内容给了它自己的样子，剩下的就是耐心：改一处、看一眼、确认没影响别的地方，再改下一处。

现在它终于能用了，可以开始写东西了。
